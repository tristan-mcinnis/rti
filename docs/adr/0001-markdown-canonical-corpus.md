# ADR 0001: Markdown-Canonical Corpus

**Date**: 2026-05-07
**Status**: Accepted
**Author**: RTI engineering

## Context

RTI stores meeting data: transcripts, summaries, decisions, action items, speaker maps, and chat messages. The previous architecture (through migration v10) stored everything in SQLite (`rti.db`) as the canonical store. All reads and writes went through GRDB.

SQLite is fast and typed, but it created three problems:

1. **Extensibility was blocked.** External agents (Claude Code, Codex, Gemini CLI) couldn't read meeting data without running SQL queries against a proprietary schema — or without RTI running at all.
2. **The user's data was opaque.** There was no `grep`-able record. If RTI crashed or the database corrupted, all meeting history was lost in a binary blob.
3. **Dual writes were inevitable.** The user wanted a searchable corpus of meeting notes *and* RTI to query them for LLM context *and* external agents to build on them. Three consumers, one binary store — the bottleneck was structural.

The decision to make markdown canonical was documented in `docs/specs/markdown-corpus-and-companions.md` but never captured as an ADR. This document formalizes the trade-off.

## Decision

**Markdown files under `~/meetings/` are the canonical store for all meeting knowledge.** SQLite (`~/Library/Application Support/RTI/rti.db`) is a derived index and sidecar for non-knowledge data (chat messages, modes, speaker overlays, FTS5 search).

### What lives where

**In markdown (`~/meetings/YYYY-MM-DD-<slug>.md`)**:
- Frontmatter: session id, date, title, duration, mode, attendees, speaker map, key topics, transcript quality, WAV path
- Body: Summary section, Action Items, Decisions, Key Topics, Open Questions, Next Steps, Transcript section (timestamped speaker lines)

**In SQLite (`rti.db`)**:
- `chat_messages` — interaction log (user ↔ assistant), not meeting knowledge
- `modes` — configuration (system prompts, reference text)
- `session_search` (FTS5) — derived index over markdown bodies, regenerated by `CorpusFTSReindexer`
- `speaker_overlays` — cross-session speaker name corrections (applied at query time, never rewrites markdown)

### Write path

1. **During a live session**: `SessionCoordinator` writes append-only JSONL events to `~/Library/Application Support/RTI/live/<session-id>.jsonl`. One line per word/note/chat event.
2. **On session-end**: `CorpusManager.renderSession` reads the JSONL, generates title (via `SessionTitleController`), generates summary (via `SummaryController`), renders markdown via `MarkdownRenderer`, atomically writes to `~/meetings/` (`.tmp` then rename), deletes JSONL, triggers FTS reindex.
3. **Crash recovery**: On launch, `CorpusManager.recoverOrphans` scans `live/` for orphaned JSONL and surfaces them for re-render.

### Read path

- **In-app**: `CorpusBackedStore` walks markdown files, parses frontmatter, reconstructs `Session` and `TranscriptEntry` lists in memory.
- **External agents**: `rti-mcp` binary (bundled in the .app) exposes the corpus over JSON-RPC stdio with four tools: `search_corpus`, `read_meeting`, `list_meetings`, `read_live_transcript`.
- **Direct user access**: `grep`, `rg`, any text editor.

## Consequences

### Positive

- **The user's data survives RTI.** Uninstall RTI, delete `rti.db`, reinstall — the meetings are still there, `grep`-able.
- **External agents can read meetings without RTI running.** Claude Code, Codex, Gemini CLI all speak filesystem. The MCP server is a convenience, not a requirement.
- **Markdown is archival.** 10 years from now, `2026-05-03-standup.md` is as readable as it is today. SQLite schemas evolve; plain text doesn't.
- **FTS is a pure index.** Rebuild it from markdown at any time. No data migration risk for search.
- **Atomic writes prevent corruption.** `CorpusWriter` uses `.tmp` → rename, which is atomic on APFS. A crash mid-write leaves the previous file intact.

### Negative

- **Dual writes during migration.** The migration from SQLite-canonical to markdown-canonical (v11) required careful ordering: write markdown first, verify, then drop SQLite tables. The legacy tables (`sessions`, `transcript_entries`, `session_summaries`, `corpus_migration_log`) were dropped in v11 only after verifying the migration produced valid markdown.
- **No structured query over markdown without FTS.** If FTS is stale, queries are slow (walking all files). Mitigated by incremental reindex on session-end and launch-time reindex.
- **Speaker overlays are query-time only.** Corrections to speaker names live in `speaker_overlays` and are applied at FTS query/render time. Markdown files are never rewritten after creation. User edits to markdown are honored on FTS regeneration but never round-tripped back into RTI.
- **JSONL is append-only during live sessions.** If the app crashes during a live session, the JSONL may have a partial last line. Recovery code tolerates this.

## Alternatives considered

### SQLite-canonical with markdown export
Export on session-end, but keep SQLite as the source of truth. Rejected: export is a one-way door; the markdown is always lagging behind the "real" data. The user can't edit the markdown and see changes reflected in RTI.

### SQLite with FTS5 only (no markdown)
Keep everything in SQLite, use FTS5 for search, provide an MCP server over SQLite. Rejected: external agents can't read SQLite without a client library; the user can't `grep`; data is opaque to filesystem backup tools.

### Hybrid: markdown + sidecar SQLite for structured fields
Keep decisions/action_items as structured SQLite columns, with markdown for free text. Rejected: adds complexity without clear benefit. The structured fields are small enough to live in frontmatter YAML. Parsing them from markdown sections is acceptable for in-app display.
