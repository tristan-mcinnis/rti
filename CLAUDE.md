# RTI: project contract

This file provides project-specific guidance to coding agents (Claude Code, Codex — AGENTS.md symlinks here) when working with this repository.

## Build and test

`make build`, `make test`; warnings are errors. `make check` compiles every target (test bundles too), `make test-render` runs the render proofs, `make install` wraps `scripts/install-local.sh`.

## Release workflow

When making a change to RTI, verify it, commit the intended changes to `main`, and push `main`. For a change that should be used in the installed app, build from that committed revision and replace `/Applications/RTI.app` with that exact build.

**Run/install reality:** The maintainer launches the installed app at `/Applications/RTI.app`, not the DerivedData build product. When a change needs to be tested in the running Mac app, do not stop after `xcodebuild` — install via `scripts/install-local.sh` (stable signing identity, so TCC permission grants survive) and relaunch. Check binary timestamps for both paths when behavior still looks stale.

## Project identity

**Project name:** RTI (Real Time Intelligence). Use only this name in code, UI copy, bundle identifiers, and docs.

## Project focus — personal, real-time only

This is the **personal fork** of RTI: a single-user, real-time meeting copilot and the sole meeting recorder. **RTI captures and assists; it does not analyse (2026-10-17 trim).** House's job is to CAPTURE what happens, make it RECALLABLE, and ASSIST in the moment; synthesis, analysis, judging and deciding happen downstream in the `/meeting` skill and Pi. So RTI keeps capture (recording, live Soniox transcript, screenshots, the session store, archiving the raw session to the meetings folder, the automatic offline transcript upgrade) and live Notes, and the in-meeting copilot (overlay, call types, live answers, Auto cards, hotkeys). The live surface is primary; persistence is deliberately thin: each finished session archives to the sessions folder (Markdown + retained WAV legs), gets an automatic offline transcript upgrade, and is browsable on the main workspace’s Sessions page. Cross-meeting search is a local keyword scan of the notes folder via the assistant's `search_vault` tool — RTI holds no database of its own. (The 2026-08-19 "minimal" strip that removed the tabs, slash commands, palette, and vault grounding was reverted wholesale on 2026-08-28 — that experiment is settled, don't re-strip the copilot.)

**Sole recorder (2026-08-28):** RTI owns meeting recording end to end — durable WAV legs, automatic transcript upgrade, and the hand-off to the `/meeting` skill. Meeting Sentinel was deleted; nothing external records meetings anymore.

## Architecture

Single-process macOS app. Coordination is distributed across `@Observable @MainActor` singletons (`SessionCoordinator`, `LLMController`, `WindowCoordinator`, `CallTypeStore`, etc.), wired together by `AppDelegate`. There is no single `AppState` class — each module owns its slice of state.

**Live transcript state and saved chat have distinct lifecycles.** The active
transcript (`SessionCoordinator.liveEntries`, a read-through to the pipeline's
array with `transcriptRevision` as its observed revision, never a second
copy) stays session-scoped. The
2026-09-17 approved chat contract retains each submitted conversation and its
attachments for later follow-up: structured threads belong to the existing
vault RTI owner under `chats/threads/`; immutable attachment and credential-free
request blobs belong to local `Application Support/RTI/chat-assets/`. This is
an explicit exception to the old session-only attachment rule, not permission
for an RTI database, semantic index or expanded capture. `/new` clears the
active chat and pending context but does not erase its saved thread or stop
recording. Retain saved chat content until explicit deletion; no automatic
pruning. Daily logs and meeting chat exports are compatibility projections
linked to the owning structured threads, not independent histories.

The durable per-leg recordings (`MeetingRecorder`) are the only audio copy
and remain in the session archive (the old temp mic WAV is gone). Do not duplicate those audio
or frame owners in the chat asset store. Config on disk: API keys in
`CredentialStore`, the call type in `UserDefaults`.

**One deliberate exception — the session archive.** When a session ends, `SessionArchive.write` (called from `SessionCoordinator.completeStop`) saves a Markdown record of that session at `<sessions_dir>/<yyyy-MM-dd HHmmss>/` (`sessions_dir` in RTI's config, `~/.config/rti/config.json`; default `~/Documents/Work/Inner-Chapter/meetings/sessions`): `transcript.md` (the live transcript with user notes inline — notes are `LiveEntry` rows with `speakerId == "note"`) and `chat.md` (the assistant chat log, only if non-empty). Alongside it, `VaultLogStore` appends one JSONL line per assistant turn to `…/rti/turns/<yyyy-MM-dd>.jsonl` (prompt metadata + output; session **or** standalone chats). These text records — plus config — are what's kept across sessions. While recording, a checkpoint rewrites the archive every 5 minutes: the snapshot is taken on main (`SessionFinalizer.prepare`) and rendered and written on a utility task (`SessionFinalizer.write`); `ArchiveWriteGate` keeps the stop's own write after any checkpoint still writing. After a transcript upgrade, typed names on the other side move to the upgraded speaker heard at the same times (`SpeakerNameRemap`; the live map stays in `speaker-names.live.json`; guided sessions keep their names on the live IDs). **Audio is kept**: `audio-mic.wav` / `audio-system.wav` land in the archive folder and feed the automatic transcript upgrade. The Sessions browser (`SessionsControlView`) lists and renders archived sessions in-app. What must NOT come back is RTI-side indexing: no embedded DB, no in-app full-text/semantic index — retrieval is the keyword scan behind `search_vault`.

Three pipelines feed into the app:

1. **Audio pipeline** — `AVAudioEngine` tap → 16 kHz mono PCM → Soniox WebSocket (`wss://stt-rt.soniox.com/transcribe-websocket`, hosted: live transcription leaves the Mac) → interim + final transcript entries held in memory (`TranscriptPipeline` → `SessionCoordinator.liveEntries`). System-audio (the other party) is captured on a second Soniox leg via the `SystemAudioCapturing` protocol: a CoreAudio process tap (`CoreAudioTapCapture`, macOS 14.2+, preferred — no Screen Recording permission, doesn't disturb screenshot OCR, follows the default output device) with `ScreenCaptureKit` (`SystemAudioCapture`) as automatic fallback. `AudioPipeline` picks the backend at start. Apple Voice-Processing I/O (acoustic echo cancellation) is an opt-in toggle (`AudioCaptureManager`, `AudioSettingsDefaults.echoCancellationKey`) — it cancels the other party's speaker bleed so it isn't double-transcribed. **Default OFF (2026-06-09):** on some Macs VPIO, enabled on an input node we only *tap* (no running output graph), delivers silent buffers and kills transcription entirely. Leave it off until VPIO is wired with a live output; the system-audio tap already captures the other party separately.
2. **Screen pipeline** — explicit `SCScreenshotManager` capture + on-device Vision OCR. A manual screenshot can be sent as image content directly to the chat's effective vision-capable provider, including cloud DeepSeek. It does not require an extra local-vision description first. Show that destination before Send and retain the submitted screenshot with its chat, per the approved 2026-09-17 retention contract. During a recording, session-scoped frame archival and ambient OCR remain separately governed by their existing controls. The optional local-models description lane runs only when ambient description is enabled; an enabled `local_vision` block alone does not mean every image stays on this Mac. **Screen privacy (2026-08-30):** deny-listed windows (`ScreenPrivacy.swift`, editable in Settings → General) remain excluded at the shared `SCContentFilter` so their pixels never enter the captured image. Chat retention must not widen those capture permissions.
3. **LLM pipeline** — provider-agnostic OpenAI-compatible streaming chat (default DeepSeek at `https://api.deepseek.com/v1`) via SSE. Provider config lives in `RTI/Sources/LLM/LLMProvider.swift` (`LLMProviders` registry); swap by changing `LLMProviders.activeId`. Prompt shapes: Assist, "What should I say?", Follow-up questions, Recap. Recent-transcript context for each turn is built from `SessionCoordinator.liveEntries` (last 15 minutes, `LLMController.contextWindowSeconds`), not from any stored transcript. Chat history is capped (`PromptBuilder.historyTurnCap`, `historyCharacterCap`): each turn sends at most the 12 newest prior exchanges (a question and its answers) in about 24k characters. The latest user turn and the newest prior exchange are always sent, and a cut history never starts with an assistant message.

"Undetectability" = `NSWindow.sharingType = .none`. POC-1's `screencapture -x` test confirms exclusion against that capture path; QuickTime and Zoom are user-attested (see `RTI/POC1-findings.md`).

Global hotkeys use Carbon `RegisterEventHotKey` so they fire from any frontmost app. Registrations live in `RTI/Sources/UI/HotkeyCoordinator.swift` — that file is the source of truth, not the README table.

## Conventions

- **Secrets**: never commit API keys, never put them in `UserDefaults`, never `.env` files. Keys live in `CredentialStore` (backed by `~/Library/Application Support/RTI/credentials.json`, mode 0600). `RTI/Sources/Secrets.swift` is gitignored, so a fresh clone needs `cp RTI/Sources/Secrets.swift.example RTI/Sources/Secrets.swift` (a keyless stub) before `xcodegen generate`; CI does the same.
- **SwiftFormat**: CI lints only newly added Swift files (the legacy tree predates the rules). Run `swiftformat --lint <new file>` before you commit a new file. Never mass-reformat legacy files.
- **Paths and binaries, one resolver each**: local config files go through `AppSupportPaths` (`~/Library/Application Support/RTI`); everything in the notes folder goes through `VaultPaths` (`~/.config/rti/config.json` anchors it; `sessions_dir` places the session archives); external executables (`claude`, python) go through `ExternalTools`. Never hardcode `/Users/...`, never `FileManager.urls(for: .applicationSupportDirectory)` at a call site, never a bare `Process()` with a literal executable path outside those helpers.
- **Transcript semantics**: Soniox emits words with `is_final: false` (interim, update in place) and `is_final: true` (commit, appended to the in-memory `liveEntries`). `SpeakerLabelMapping.rawLabel(speaker:channel:)` is the one mapping: mic leg speaker 0 or 1 → `"self"`, 2+ → `"room_N"`; system leg → `"remote_N"` (speaker 0 folds into `remote_1`). The live view shows `You`, `Room speaker N`, `Speaker N`, and a live name always wins. The channel-less `rawLabel(speaker:)` (file mode) still maps 0 → `"self"`, 1+ → `"them_N"`. Live system-leg diarization is OFF by default (`SessionSpeakerPolicy.liveLabelsEnabled`, 2026-11-12 trial: real-time clusters flip between numbers in groups, and a wrong label misleads more than none); live rows say Me or Them, typed names still reach the assistant, and the after-call file transcript keeps speaker labels (`labelsEnabled`). Live paragraphs break only after a sentence end, following a 0.5 s pause between words or past 80 characters; a mark never starts a row. Both legs are kept verbatim: `TranscriptPipeline` removes no echo, and one leg never changes the other. When the other party's voice leaks from the speakers into the mic, it shows as extra "Me" rows (live labels are off by default). The only fixes are the opt-in VPIO toggle, headphones, or Listening only. The guide, codebook and research Auto passes alone leave such echo turns out of their prompts (`TurnRoles.micEchoIDs`, below); the transcript and the archive keep them. The live view groups rows into one-label turns (`LiveTranscriptPresentation.turns`). A long turn is drawn as blocks of at most 12 rows or 2 minutes (`blockRows`, `blockMs`); a block ends only after a row that ended a sentence (forced at 24 rows), and later blocks carry no label (`Turn.isContinuation`). Each `Turn` stores its paragraphs when it is built.
- **Streaming responses**: The LLM SSE parser handles the `data: [DONE]` sentinel and concatenates `choices[].delta.content`. DeepSeek's `reasoning_content` field (gated by `LLMProviderConfig.supportsThinking`) is surfaced through a separate `onReasoning` callback. `StreamCoalescer` batches answer deltas: it writes at most every 80 ms or at a paragraph break, and the owner flushes it on finish, error, Stop and checkpoint, so the saved answer is complete.
- **Soniox context**: `MeetingContextStore.sonioxContext` builds one `SonioxContext` (setting, project, meeting, participants, and terms from the project's optional `soniox-terms.txt`). Live snapshots it at start. `session.json` keeps the end-of-call version, with renamed speakers, for the upgrade. Prep notes, briefs and project files stay out of it. `SonioxContext.forMeeting` caps the size, because Soniox refuses an oversized context and that stops the session.
- **Soniox reconnect policy**: exponential backoff 1s → 2s → 4s → 8s, max 5 retries, then surface error. Every socket is a new stream whose word timestamps restart at 0 (a reconnect, the system leg rejoining after a park, a client swap); `AudioPipeline.onStreamRestarted` re-bases that leg on the session timeline via `TranscriptPipeline.restartStream`. `SonioxClient` acts only on the current socket's lifecycle events. Its socket events arrive and frames decode on the client's own serial `callbackQueue`, not on main; words, status and errors hop to main in arrival order.
- **Swift/SwiftUI scope**: the overlay is a hand-rolled titled `NSWindow` (`OverlayWindowController`; a normal Dock-app window since 2026-09-01, no float, no translucency), not a SwiftUI `WindowGroup`. SwiftUI is used inside the window via `NSHostingView`.
- **No RTI database or index**: durable chat threads and meeting records stay with the existing vault owner under `…/databases/projects/personal/rti/`. The approved local `chat-assets/` exception retains submitted attachment bytes and request snapshots, not a second conversation registry. Keep assets owner-only, out of Git and automatic vault ingestion, and eligible for ordinary local backups. Do not configure a new cloud sync. Structured threads reference assets and existing meeting artifacts; deletion must respect references and never remove original user documents or linked recordings. The `/meeting` skill owns meeting processing.
- **Shared chat implementation**: consume house-chat-core at the macOS 14 floor. It is its own repo (extracted from quick-launch 2026-10-16, one package, two consumers), pinned by GitHub URL and tag in `RTI/project.yml`, so a fresh clone builds with no sibling folder; the design tokens come from the design-system package the same way. To take a change, raise the `from:` pin, regenerate with xcodegen and commit the resolved file. Share command/context/schema/extraction interfaces, not app defaults or histories. The approved implementation contract is `../quick-launch/docs/chat-harmonization-plan-20260917.md`; a combined history remains future exploration.
- **Dependencies**: keep SPM deps minimal — only add when a feature needs it (current set: Starscream, Yams, MarkdownUI). GRDB was dropped in the personal refocus.

Cards use `text_en`, `text_zh`, `why` and `source`. Code then drops (`AutoCardRules.accept`): a RECALL without a supplied source; a SAY or ASK without `text_zh` when more than 30% of the window is CJK (a Mandarin-only line, in either field, counts as its Mandarin line, and an older saved prompt's three-line `text` splits: `AutoCardLanguage.lines`); a card with Jaccard 0.5 or more against one shown in the last 15 minutes; on research, every card after the first unless it is a FLAG quoting two call times; with no guide running, a card that names a guide. The rail shows the Mandarin line first, then pinyin made on this Mac (`AutoCardLanguage.pinyin`; Settings > General "Show pinyin under Mandarin cards", `AutoAssistSettings.pinyinKey`, default on), then the English line as a small gloss in the same block (none when the card has one line); the why line sits apart in a quieter tone; Copy takes the Mandarin line. The prompt puts stable parts first for provider caching (contract, framing, language rule, brief, project context, guide section budgets, guide position), then the last 20 surfaced cards plus one topic line for older ones, codebook tensions and hypotheses (top 10, research), signals (a section over its budget, no Them speech for 3 minutes; research), gaps, notes, vault, earlier context, the Mandarin line and the new window. `LiveRailPacer`/`LiveRailBoard` pace what the rail shows (one item per 60 s, a 4 s hold after your own speech on client calls, lane caps 3 and 2, fade after 4 min). Only cards the user saw count as already surfaced: a card that faded unseen may return in a later pass. A guided research call also runs the Notes, Codebook and Guide passes on the shared tick (120 s default, about 30 an hour each), so its background LLM calls are about 150 an hour, plus about 6 codebook synthesis calls (every 10 minutes). The rail draws the guide only on research calls; a guide on another call type keeps its tab and brings no rail. On research calls the Auto prompt names a guide question only while it is fresh: the user's pick, a marker link, or a guide pass position under 4 minutes old (`GuideSessionController.autoQuestion`); otherwise it says "Guide position uncertain". Guide gaps go in only while a guide pass succeeded in the last 4 minutes (`autoGaps`), and research transcript lines carry the `TurnRoles` hint (`Them, moderator`). Each Auto pass searches the picked project with a short query from `AutoVaultQuery` (the 12 most salient terms of the new window, English and Chinese filler dropped, no search under 25 words) and `broaden: false`, so it never scans the whole vault; the `search_vault` tool keeps its default (`broaden: true`). Auto's search runs at most once every three passes (`AutoVaultCadence`; the passes between reuse its hit) on `VaultSearch.Budget.auto` (`.utility`, two workers, stopped after 300 ms or when the pass is cancelled; the walk checks every enumerated item and may use only the first half, and each worker reads at least 8 files, newest first) with a per-session in-memory `VaultSearch.DocumentCache` keyed by path, modification date and size (lowercased text only, capped at 16 MB). It is not an index and is never written to disk. Pass timing state is not observed (`pass` is `@ObservationIgnored`; views read the stored `isGenerating`), and the self-speech time stays outside the observed rail, so a flush of finals does not redraw the rail. The scheduler staggers its tasks inside the interval (`ScheduledTask.phase`: Notes +0, Auto +1/6, guide +1/3, codebook +2/3, synthesis +5/6). Guide and Codebook passes read `GuideTranscript.liveSources()` over the pipeline's incremental utterance index (`TranscriptPipeline.utterances`, `UtteranceIndex`), never a full regroup; `PassSignpost` (category `LivePerf`) times each pass prep. Results and card states live in memory only. **The old Discussion Guide ledger, Findings (intelligence ledger), the end-of-session summary and generated title, and the saved-meeting outputs were removed 2026-10-17 (analysis belongs downstream); don't revive them. The research Guide and Codebook capture evidence live; they are not that ledger.**
- **Research turn roles (2026-11-12)** → `RTI/Core/Guide/TurnRoles.swift`, one pure rule shared by the guide pass, the codebook pass and the research Auto pass. With live labels off every system-leg turn is one speaker, so it gives each turn a role hint (`SpeechRole`: moderator, respondent, unknown). A turn is moderator speech when it is on the mic leg, on a seat assigned to the moderator, ends in a question mark or in 吗 (a full stop after 吗 is allowed), is a restating summary (所以…对吧) or a show-of-hands call, or matches guide wording (`GuideMatcher`: character 4-gram Dice overlap 0.35 or more, at least 3 shared). 呢 alone never makes a question: 我还没试过呢。 is a respondent's. A bare 对/嗯 is unknown. `GuideTranscript.sources` splits a turn after a question mark with more words after it; the later piece starts at a time interpolated by character offset. That time moves while the utterance grows, so the ID never uses it: piece k of `speaker@start` is `speaker@start#pk`, and a consumed piece is never sent or filed twice. Mic-leg echo turns are dropped from these prompts only on an in-room group heard on a speaker (`TurnRoles.micEchoIDs`). Three tests must hold: the last 10 minutes show the room on both legs (`roomOnBothLegs`: at least 3 echoes, and at least half of the mic turns), the mic turn overlaps system-leg speech for half its length or more, and 80% or more of its unit pairs occur in that speech (word pairs in English, character pairs in Chinese, `echoPairs`). A remote IDI or client call drops nothing. The pass still consumes a dropped turn. Moderator-role turns never supply a guide quote or note or a codebook entry. Count quotes, never people.
- **Research guide pass (2026-11-12)** → `RTI/Sources/Notes/GuideSessionController.swift` + `GuidePrompt.swift`; decode in `RTI/Core/Guide/GuidePass.swift`. The model files each respondent turn anywhere in the guide; the current question is a hint, and only a manual pick or a marker link fixes where a turn files. The payload gives section titles and minute budgets, full wording for the current section and its neighbours, and a qid and title elsewhere. A moderator line that reads or closely paraphrases a guide question sets the position on its own (`GuideMatcher.question(asked:near:)`; a repeated block resolves to the nearest copy ahead); every such line in a batch counts, in spoken order. Moderator lines and bare backchannels (对对对, role `unknown`) never supply a quote or a note. The decode is tolerant: `suggestion` may be a string, an object with `qid` (its `ids` join `evidence`) or null; `votes` default to empty; a bad field drops only itself. A moderator's spoken show-of-hands count is a vote record (`count`, `source: moderator_tally`; older `guide-cells` files load unchanged) and the cell's tally reads "5 chose B (show of hands)". A count must rest on a moderator line that names the choice: the cited turn, or the piece just before it from the same utterance (选A的呢？ before 一位。). A count on a respondent's line is dropped. Seat-attributed picks in the same cell stay visible after the count ("Named picks: 1 of 6 chose B"), never summed with it. A failed pass is retried once at its own size, then given up and the capture marked incomplete, so a failure never doubles the next prompt. After 3 empty passes in a row the scheduler's ticks run every third time until a pass files something; a backed-off tick still checks its ready turns locally, and a moderator line that moves the position ends the back-off. The Guide tab's refresh button skips the back-off.
